# AFS Spectroscopy Assessment

**AI assistant for in-line spectroscopy solution design** – built by **Team Hallucination Nation** (Felix Heinemeyer, Dominik Wittenhagen) for the National AI Hackathon 2026 by SchubKI, challenge by Art Fiber Systems (AFS).

An AFS expert pastes a customer enquiry. The assistant turns it into a first technical assessment: which facts the customer stated, which are missing, which assumptions in the request contradict the AFS material, which spectroscopy setups are worth testing and why, and what a first feasibility experiment should look like. Every recommendation is traced to a page in the AFS material, and every decision of the assistant can be confirmed or changed by the expert.

**Live app:** https://afs-spectro-assistant.felix-afs.workers.dev

**Answers for the final evaluation scenarios H01–H06:** [`answers/`](answers/README.md) – generated by `node scripts/answers.mjs`, without manual editing or case-specific code.

## How it works

The assessment follows the columns of the AFS method comparison table (S01 Table 1, p.6) as a **decision path** of six steps:

| Step | Question | Values |
|---|---|---|
| Sample state | What is the sample at the measurement point? | powder, clear / turbid / opaque liquid, melt or paste, soft solid or tissue, rigid solid |
| Measurement interface | Where and how is it measured? | in-process probe, non-contact at a distance, laboratory samples |
| Usable spectral range | Which light reaches the sample through the fiber link? | UV/Vis/NIR only (silica), mid-IR possible |
| Measurement target | What must be measured? | chemical composition, turbidity / cell density, fluorescent species, classification |
| Optical variability | Do turbidity, texture or optical density change? | stable, changes |
| Concentration level | How much of the target is present? | major, minor, trace |

For each step the assistant decides whether the value is **stated by the customer** (with the quoted sentence), a **suggestion** from the AFS material that the expert confirms, a **conflict** between the customer text and the AFS material, or **missing**, in which case it becomes a clarification question. Nothing that is not stated is treated as fact.

From the decided steps, a rule engine:

- **ranks the 19 method setups** of the AFS table (e.g. NIR diffuse reflection probe, MIR ATR probe, Raman probe) with pros, cons and conditions, each with a source;
- runs a **premise check** on the request. Examples: reusing a silica fiber for mid-IR, quoting a lab study as clinical proof, fluorescence without a fluorescent target, asking for a final specification while decisive facts are missing;
- shows, for every open step, **which answer would remove or restrict a method**. Results stay explicitly *provisional* until every step is decided.

The expert walks through the path, accepts or changes values, adds notes, and can:

- copy the open questions as an e-mail to the customer;
- compare the shortlisted methods side by side;
- generate a **written assessment** in the structure of the AFS worked examples, with sources and PDF export;
- add the finished case to the knowledge base as a **solved case** that later shows up next to similar enquiries.

## System architecture

```
                         ┌──────────────────────────── Cloudflare Worker (worker/) ──────────────────────────────┐
 Browser (React, src/)   │                                                                                        │
 ─────────────────────   │  POST /api/tree   Clef pipeline (worker/clefSteps.ts)                                   │
 enquiry ───────────────►│    A  Clef classifies the 6 steps + premise facts from the customer text               │
                         │    B  Clef rates every knowledge card: relevant to this customer?                      │
                         │    C  Clef classifies the steps again with the relevant cards                          │
                         │    rules: stated / suggestion / conflict / missing (confidence thresholds)             │
                         │    D  Clef rates each card against the decided value: supports · caution · background  │
                         │    E  Clef picks the sentence of the enquiry that states the value (customer quote)    │
 decision path ◄─────────│    + derived steps (silica link → UV/Vis/NIR only) + premise check                     │
                         │                                                                                        │
 rule engine (shared/)   │  POST /api/report  gpt-oss-120b writes the assessment from the fixed results;          │
 ranking, premises,      │                    unknown citations are removed; cached per input (KV)                │
 open questions          │  /api/docs, /api/docs/:id/cards   knowledge base: PDFs, page texts, knowledge cards    │
                         │  /api/cases        solved cases (expert decisions + notes)                             │
                         └──────────────────────────────┬─────────────────────────────────────────────────────────┘
                                                        │
                           Workers AI: @cf/cloudflare/clef (classifier) · @cf/openai/gpt-oss-120b (text only)
                           KV namespace DOCS: page texts, card edits, uploads, solved cases, report cache
```

**Why a classifier instead of a chat model for the decisions:** reproducibility. A language model gave different decision paths for the same enquiry in about 20–27 % of runs, even at temperature 0 and with majority voting. The Clef classifier answers fixed multiple-choice questions with probabilities, so the same enquiry and the same knowledge cards always give the same decisions (100 % identical in our benchmark). The language model is used only where variation does not matter: to *write* the final assessment from results that are already fixed.

- **Frontend:** React 19 + TypeScript + Vite. The decision path is an SVG "fiber" chart. History and settings are stored in the browser.
- **Backend:** Cloudflare Worker (TypeScript) with Workers AI and one KV namespace.
- **Shared logic** (`shared/`): the step definitions, the rule engine, the method table and the report input. It is used identically by the browser, the worker and the scripts.

## How the assistant uses the AFS knowledge base

1. **Knowledge cards instead of free retrieval.** Each document is read *once* and turned into knowledge cards: a short claim, the decision step and value it speaks to, the page, and a **verbatim quote** checked against the PDF text.
   - The cards for the AFS originals S01–S04 (74 cards) are curated and versioned in [`knowledge/cards/`](knowledge/cards/).
   - Every assessment uses exactly these cards, which is what makes the results reproducible.
2. **Clef reads the cards per step and per customer** (stages B–D above). Only cards that support or qualify the decided value for *this* customer are shown as references. Each one opens the PDF at the cited page with the passage highlighted.
3. **Rules from the AFS material.** The method table S01 Table 1 is transcribed in `shared/knowledge.ts` from `AFS_method_comparison_table.xlsx`, and the fiber transmission ranges come from S02 p.6. Each rule in `shared/engine.ts` carries its source and page, e.g. "transmission saturates in opaque media – S01 p.16" or "silica fibers 0.35–2.4 µm – S02 p.6".
4. **The AFS originals are the main source.** The evaluation and the H01–H06 answers use *AFS originals only*. One open-access review (A01, see [Third-party sources](#third-party-sources)) is bundled as an *added source* and is used only when the expert switches to "Originals + added sources". Experts can upload further PDFs, which are read into cards by the language model and can be reviewed card by card.
5. **Solved cases.** The worked examples D01 and D02 from the AFS reference document are included as solved cases ([`knowledge/cases/`](knowledge/cases/)). Cases finished by an expert are added next to them. They are shown for reference next to similar enquiries and **do not influence the decisions**.

S05 (flyer) and S06 (website link) are business context, not technical evidence, and are not used for recommendations.

## Setup and run

### Prerequisites

- **Node.js 22.18 or newer** (the scripts import the TypeScript modules in `shared/` directly) and npm.
- A **Cloudflare account** (Workers AI with Clef and gpt-oss; we used the Workers Paid plan). Workers AI also runs remotely during local development, so you need to log in once.

### Install and start locally

```bash
git clone https://github.com/felixwallst-eng/afs-spectro-assistant.git
cd afs-spectro-assistant
npm install
npx wrangler login                 # once – Workers AI is used from your Cloudflare account
npx wrangler kv namespace create DOCS
#   → copy the printed id into wrangler.jsonc (kv_namespaces[0].id), replacing ours
npm run dev                        # http://localhost:5173
```

No API keys or `.dev.vars` are needed: the worker uses the Workers AI binding of your account.

### Use the app

1. Open http://localhost:5173. On the first load the app indexes the bundled PDFs (page texts into KV, a few seconds).
2. **Assessment** tab: paste an enquiry or pick one under *Example* (D01–D08, H01–H06), then choose **Analyse enquiry** (about 3–5 s). The evaluation cases H01–H06 are also pinned in the sidebar with stored results.
3. Walk through the decision path with ← → and confirm or change each step. Then use *Questions for the customer*, *Compare all methods* and **Write assessment** (with PDF download).
4. **Knowledge base** tab: documents, their knowledge cards, upload of further PDFs, and the solved cases.
5. **Settings** tab: confidence thresholds (see below).

### Deploy

```bash
npm run deploy                     # build + wrangler deploy (Cloudflare Workers)
```

## Model and tool configuration

| Setting | Default | Where |
|---|---|---|
| Decision engine | **Clef classifier** `@cf/cloudflare/clef` – fixed in the app (an LLM pipeline, `worker/steps.ts`, is kept only for the benchmark comparison) | `worker/clefSteps.ts` |
| Decided threshold | **0.50** – a value read from the text with this confidence counts as stated | Settings page, `shared/types.ts` (chosen with `scripts/thresholds.mjs` on D01–D08, no errors) |
| Suggestion threshold | **0.30** – between this and "Decided" a value is suggested for confirmation; below, the step is missing | Settings page |
| Premise threshold | **0.50** – facts from this confidence on feed the premise check | Settings page |
| Language model (written assessment only) | **gpt-oss-120b** `@cf/openai/gpt-oss-120b`, temperature 0 – fixed | `worker/report.ts`, `shared/agent.ts` |
| Knowledge sources | **AFS originals only** (S01–S04); optional "Originals + added sources" | Assessment page |
| Pipeline version | `clef-v6` | `worker/clefSteps.ts` |

## Loading the AFS materials

The supplied materials are already part of the repository, so no extra step is needed:

| Material | In the repository |
|---|---|
| S01–S04 PDFs | `public/sources/S01.pdf` … `S04.pdf` (served to the PDF viewer) |
| Knowledge cards for S01–S04 | `knowledge/cards/S01.json` … `S04.json` (curated, quotes verified against the PDF text) |
| AFS method comparison table (xlsx) | transcribed as `BASE_METHODS` in `shared/knowledge.ts` (19 setups with sensitivity, selectivity, cost, optical path) |
| Fiber families (S02 p.6) | `FIBERS` in `shared/knowledge.ts` |
| Scenarios D01–D08, H01–H06 | `eval/cases.json` (verbatim) |
| Worked examples D01, D02 | `knowledge/cases/reference-cases.json` (as solved cases) |

To update a document's cards, use **Knowledge base → Cards** to remove cards or re-read the document, and **Reset to curated** to return to the files in the repository. To add a new document, upload the PDF on the Knowledge base page. It is read page by page into cards, which you can then review.

## Reproducing the answers and the evaluation

All scripts talk to the running app (`npm run dev`, or `--url https://<your-worker>`).

```bash
node scripts/answers.mjs                                  # answers for H01–H06 → answers/*.md + *.json
node scripts/answers.mjs --set dev                        # the same for D01–D08 → answers/dev/
node scripts/repro.mjs --experiments clef --runs 3        # reproducibility + quality on D01–D08
node scripts/repro.mjs --experiments clef --set traps --runs 1   # own premise trap cases T01–T10
node scripts/thresholds.mjs                               # threshold study from the logged Clef answers (no calls)
node scripts/citations.mjs --show                         # citation quality against eval/gold/citation_gold.json
node scripts/export-demo.mjs                              # stored H01–H06 results for the sidebar
```

The answers are produced by the same code path as the app, with no expert input:

1. Clef decides the steps and the rules run.
2. `shared/reportInput.ts` collects the fixed results and the evidence.
3. The language model writes the text.
4. The script renders Markdown.

Decisions, methods, premises and sources are reproducible. Only the wording of the text can differ between runs, and it is cached per input.

Gold standards (drafts by the team, D cases only) are in `eval/gold/`, and benchmark outputs in `eval/results/`.

## Results

Measured with `scripts/repro.mjs` (Clef pipeline, AFS originals only):

| Set | Result |
|---|---|
| Development D01–D08, 3 runs | **48/48** decision steps within the gold standard, **0** wrong values stated as customer facts, **100 %** identical decision paths across runs, ≈ 2.5 s per enquiry |
| Own trap cases T01–T10 | **11/11** expected premise findings, 0 false alarms |
| Final H01–H06 | **7/9** expected premise findings, 0 false alarms (two "certainty" premises missed) |

For comparison, the language-model pipeline found 8/9 premises on H01–H06, but stated 24 wrong values as customer facts on D01–D08 and was not reproducible.

## Limitations

- **The enquiries are underspecified on purpose.** Concentration range, optical variability and fiber link are rarely stated, so most assessments stay provisional. The assistant asks for these facts instead of guessing.
- **Requests for certainty are hard to detect.** The "certainty" premise is missed when a request mixes "give us the final configuration" with exploratory wording (H04, H05).
- **The rules know only what the AFS material says.** Chemistry beyond the sources (e.g. which band an analyte absorbs in) is not modelled; spectral ranges are nominal method ranges, not instrument specifications.
- **Some limits of the knowledge and the data:**
  - Cards for uploaded documents are created by a language model and should be reviewed.
  - The gold standards are drafts by the team.
  - Solved cases are not yet used by the classifier.
- **Wording of the written assessment can vary between runs**, while the underlying decisions and sources do not.
- **Local data:** history and settings live in the browser; knowledge base and solved cases live in the Cloudflare KV namespace.
